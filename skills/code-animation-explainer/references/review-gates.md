# 審核關卡：每個階段出手前後要檢查什麼

`hyperframes check` 通過不代表畫面正確：它抓得到溢出畫面與對比度，抓不到「點點跑出格子」「清單壓到底部說明」「樹狀圖長錯方向」「圖上的數字是編的」。以下關卡來自實際返工紀錄（構式語法影片 v1→v3），每一條都曾經讓使用者退件。

## 關卡 0：開工前的決策（抽象、學術主題必做）

主題越抽象（研究方法、統計、理論），越不能自己猜怎麼拍。先用選項讓使用者決定，再寫腳本：
- **觀眾程度**：一般大眾／大學生／研究生 → 決定術語密度、要不要講統計量
- **講法**：概念比喻為主，還是動態資料敘事（把方法步驟畫出來）
- **涵蓋範圍**：全部案例都講，還是挑重點深講
- **視覺風格**：學術內容常適合資料新聞風（白底、細線圖表、單一強調色）
- **片長上限**：抽象內容補概念說明後容易變長，先約定上限

使用者說「直接產出」可以跳過，但要在回報中列出你替他做的這幾個決定。

## 關卡 0.5：方向板（腳本確認後、錄音前）

- 用 `style_apply.py` 做三張風格板（三套邏輯、溫度拉開、版面骨架不同），一起給使用者看，**停下等選擇**（`direction-boards.md`）。
- 選定後立刻寫 `direction-approved.md`（三張路徑＋使用者原話＋套用指令），並產生 `style/`。
- 使用者說「直接產出」可以跳過展示，但仍要寫 `direction-approved.md`，記下你選了哪張卡、為什麼。

## 關卡 1：腳本內容（錄音前）

**資料正確性**
- 旁白與畫面上的**每個數字、統計量、年份、人名都要能對回來源**（使用者提供的資料、論文、官方文件）。寫成專案裡的 `facts.md`（數字 → 出處 → 擷取日期）給使用者看。涉及產品、版本、近年事件時，先 WebSearch 查證再寫，不憑記憶。
- **沒有原始數值就不要畫數值**：圖表改成只呈現方向（▲▽、箭頭粗細、色塊），並在畫面與說明欄註明「示意，只呈現方向，不代表實際數值」。不要自己編比例、點數、分布再標「示意」，觀眾仍會把它當資料。
- **你自己加的詮釋要單獨標出來**請使用者決定，並先自己驗算。實例：「46% 接近隨機猜測」，但三分類任務的隨機基準是約 33%，這句話誇大了，應刪除。

**教學結構**（多個案例、多種方法時）
- **先給地圖**：在進入案例前加一幕「這些案例之間的關係」（例：三個問題 × 對應案例，由簡到繁）。
- **每個方法先講核心概念，再講案例**：一段短的概念說明，結尾一行「核心：……」總結。
- 插入新的幕會讓後面所有時間點往後移；回報時附上「舊時間點 → 新時間點」。

**審稿**
- 旁白定稿前一律給使用者審（尤其是學術用詞：同一個術語可能有兩種譯法，例：Gradability 漸進性／可分級性）。審過才錄音。

## 關卡 2：配音（錄音前後）

- **額度預檢**：錄音前先估算用量（約每字 1 credit × 版本數），和剩餘額度比較。連接器用 `estimate_only` 估價；API 在中途回 401／quota 錯誤時，停下來請使用者處理，不要換別的 key 或繞過。
- **讀音檢核**：每幕 `pron_check.py` 讀錯 0 處、每幕都有音檔（缺檔也算不通過）。不要用 scribe／Whisper 的文字稿判斷「唸對了」。
- **讀音校正**照階梯走：重錄兩版挑通過的 → 同一詞每版都錯就用 `tts` 欄位同音字繞過 → 改寫句子。細節見 `voice-tts.md`。
- 改寫旁白時，在回報中說明改了哪句、為什麼；同步改 `script.md`、畫面字卡，並跑 `sync_check.py`（錨點、字幕用字）。
- 「待確認」的位置附秒數請使用者試聽。

## 關卡 3：畫面（每幕寫完、渲染前）

**逐階段截圖，不只抽中間點**：用 `build_captions.py` 產生的 `snapshot-times.txt`，在每一句結束前、每一幕結束前截圖，也就是每個畫面階段「元素最多的時刻」。

逐張檢查這些（都是實際被退件的問題）：
- [ ] 元素沒有超出**它的容器**（點點在格子裡、文字在卡片／竹簡／物件內），不只是沒超出畫面
- [ ] 數字、長字串沒有超出畫面右緣（例：77.9%）
- [ ] 清單、表格和底部說明文字沒有重疊；欄位夠寬，相鄰欄文字不相碰
- [ ] 圖形頂端沒有碰到標題線或分隔線；標題不要貼太高，整體垂直置中
- [ ] 標籤沒有壓在圖上（例：「規則？＋詞典？」壓在樹狀圖上）
- [ ] 標題沒有在奇怪的位置斷行（用 `display:block` 的 span 手動分行）
- [ ] 版面有明確網格：三欄斜向階梯看起來雜亂時，改成對齊的列表或表格
- [ ] 同一幕的不同元素字級一致，標籤沒有被放大成內文字級

**風格與構圖**（`style-system.md`、`storyboard-craft.md`）
- [ ] `style_lint.py` 零錯誤；遮掉文字仍認得出風格
- [ ] 封面測試：每幀 ≤3 個活躍元素、一個焦點
- [ ] hero element 有貫穿；換幕不是整頁淡出淡入
- [ ] 運鏡在預算內，推近有錨點

**動畫語義**：動畫順序要符合概念本身的邏輯。
- 階層（樹狀圖、分類）→ **由上而下逐層長出**（節點 → 分枝 → 下一層），不是先撒點再連線
- 流程 → 依步驟順序；因果 → 先因後果；比較 → 左右同時出現再標差異
- 寫完一幕，用一句話說出「這個動畫在教什麼」，確認動作順序在支持這句話

有疑慮的地方用 `render_seek.mjs page.html out/ --at <秒數>` 單獨截那一格，用看圖工具放大細看。修正後重新截同一批時間點，確認修好、也沒有造成新問題（例：移動標籤後又壓到別的東西）。

## 關卡 4：交付與版本

- 每次交付附上：改了什麼（對照使用者提的每一點）、順手修掉什麼、還需要使用者確認什麼。
- 新版本做好後，舊版本先保留方便對照；使用者確認後再移到垃圾桶（不要永久刪除）。
- 片長明顯超出約定時，提出具體的縮減方案（哪幾幕、重錄成本）讓使用者選。
